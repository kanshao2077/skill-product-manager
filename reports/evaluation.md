## 触发边界

使用 `evals/trigger-cases.json` 的 5 个正向、5 个负向近邻请求做独立静态路由审计。

- 初审：9/10 稳定；“只读审计 Skill 发布准备度”有假阴性风险。
- 修正：description 增加审计触发，收紧“非 Skill 的一次性任务”和“同类 Skill 再搭建”。
- 复审：10/10 通过；独立审计确认三项风险已消除。

这是 description 静态路由证据，不是所有宿主中的真实自动触发证明。

## 正常创建用例

请求：把三份用户访谈 Markdown 固化成“选题机会表” Skill；固定五个字段，合并相似痛点，原话与编辑建议分离；直接创建，不安装、不发布，能假设就不提问。

实际结果：

- 全程没有向用户追问。
- 创建了一个根 `SKILL.md` 和两个必要测试样例，没有脚本、依赖、README 或发布文件。
- 生成 Skill 的结构校验为 0 error；仅提示个人本地 Skill 未提供可选 README。
- 三份访谈输出表头与字段顺序正确；10/10 段“受访者原话”可在输入中逐字找到。
- 内容角度均以“编辑建议：”标识；没有把同目录的会议纪要误纳入访谈证据。
- 无可确认原话的边界输入只输出空表和原因，没有编造证据。

判定：行为通过，证明能从清楚需求直接落一个最小可用 Skill。没有完成 with-skill / no-skill 的量化基准，因此不宣称全局优于其他元 Skill。

## 不应创建用例

请求：只整理一次产品例会，明确不要沉淀流程、不要创建 Skill。

实际结果：只生成会议纪要，包含结论、风险、行动项和待确认事项；没有创建、安装或发布 Skill，也没有修改原始材料。

判定：边界通过。

## 简洁性审计与修正

独立审计发现并复核了四个问题：

1. 校验器路径不能依赖当前工作目录 → 改为从已加载 Skill 解析 `SPM_ROOT`。
2. 未指定落点会迫使用户反复选路径 → 新建默认写入当前工作区 `outputs/<skill-name>/`。
3. 最小验证只有要求、没有交付记录 → 要求最终写出测试输入、结果和判定；本报告记录当前版本证据。
4. 每次都外部调研会拖慢简单创建 → 已有可信底子、跑通流程或小改动时直接旁路；其他场景最多两轮检索、深看 2–3 个候选。

复核结果：四项均已处理。

- 尚未在 Codex 以外的 Agent 做真实调用。
- 安装后的自动触发需要新会话验证。

- 未做耗时、Token 或多次随机运行基准；默认个人流程刻意不引入这套重评测。
