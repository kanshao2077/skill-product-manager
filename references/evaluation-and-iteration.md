# 评测与迭代

只在公开发布、高风险、主观质量难判断、最小测试失败或用户明确要求严格评测时读取。普通个人 Skill 不需要完整基准工程。

## 1. 先冻结成功标准

测试前写清：核心任务、能力边界、不能违反的约束、什么算通过。测试后不能为了迁就结果临时改标准。

## 2. 分清证据

- `结构`：入口、frontmatter、引用和脚本存在，只证明可加载。
- `行为`：真实任务中按预期决策并产出，只证明该用例有效。
- `对照`：同题下优于无 Skill 或旧版本，才证明有增益。
- `人审`：审美、语气、创意和复杂判断由目标用户或领域人员决定。

“应该可以”“看起来完整”不是证据。无法执行的检查标为“未验证”。

## 3. 最小用例

默认准备三类：

1. `正常`：代表性真实任务，检查核心流程和完成品。
2. `模糊/近邻`：不影响方向的缺失应合理假设；会造成方向错误或外部风险的缺失才询问。相似关键词但目标不同的请求不应误触发。
3. `失败/安全`：输入损坏、工具不可用、权限不足或越界请求；不得伪造结果或绕过边界。

为每个用例记录：输入、预期触发、必须动作、禁止行为、实际产物、判定。

## 4. 需要时做同题对照

- 新 Skill：比较 `with-skill` 与 `no-skill`。
- 改造 Skill：比较新版本与修改前快照。
- 保持模型、宿主、工具权限、输入和通过标准一致，并使用独立会话。
- 比较完成度、约束遵守、错误、追问次数和可直接使用程度；结果更长、步骤更多不等于更好。

高价值或争议结果可交给未参与编写的 Agent 做盲评。隐去版本名和制作过程，只给任务、产物和评分规则。主观任务仍需人审。

## 5. 最多两轮

每轮只处理已有证据确认的问题：定位原因、做最小修改、重跑失败用例和一个关键正常用例。

以下任一情况立即停止：

- 硬性标准已通过且相对基线有明确改善。
- 两轮后同一核心失败仍存在。
- 下一步需要新权限、重大依赖或改变原需求。
- 改善一个指标会破坏更重要约束，需要用户取舍。

停止时如实标记“通过 / 验证失败 / 未验证”，不要继续堆规则来迎合测试。
